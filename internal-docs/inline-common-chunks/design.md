# Inline Common Chunks — Design & Principles

## Summary

`output.codeSplitting.experimentalInlineCommonChunks` lets a small common chunk stop being a file. Its modules are printed, in full, into every file that reads them (unless every known entry loading path to that file already registers them), inside a registry factory (`__share(id, (exports) => { ... })`), each copy finalized and named as part of the file it lands in, and each reading file obtains the shared exports object with `__share_require(id)`. The registry lives in the runtime module, so however many copies of the factory a page loads, the modules run once and every reader sees the same live bindings. The option trades duplicated bytes for one fewer request per removed chunk. It is experimental and only exists for ESM output under `strictExecutionOrder`, which the feature turns on when the user omits it ([backlog #14](https://github.com/rolldown/backlog/issues/14)), with `preserveEntrySignatures: false` ([backlog #15](https://github.com/rolldown/backlog/issues/15)).

The contract the feature keeps, and that the differential cases in `packages/rolldown/tests/behaviors/inline-common-chunks/` check against the same build with the option off:

- Every module still evaluates exactly once, in the order strict execution order gives it, along the resolved internal static and dynamic loading paths from each configured or plugin-emitted entry.
- The files behind a record, external modules included, evaluate in the order they did with the option off: a file expands a record it reads at the position it imported the record.
- Consumers read live bindings; CommonJS members keep one `module.exports` object; `init_*`/`require_*` wrappers are shared.
- A call through a bridge sees `this === undefined` exactly as a call through an import does: every callee read through a bridge, whatever the call's form (`f()`, `f?.()`, `` tag`x` ``, a namespace-member call, a call marked pure), is printed as `(0, bridge.f)(...)`; the only bare bridge callees are the module wrappers `init_*`/`require_*`, which never read `this`, and a finalized module or record copy that holds any other bare bridge callee fails the build.
- Errors thrown while a shared module executes are rethrown identically to later readers.
- `maxSize: 0` (the default) produces byte-identical output to leaving the option out.
- A record's modules are listed in the `moduleIds` (after the file's own) and `modules` (in execution order) of every file that prints them, so `renderChunk`, `augmentChunkHash` and `generateBundle` see the code each file really contains. The module-to-chunk relation a plugin observes is therefore one-to-many for a record's modules; the option is only for builds whose plugins and consumers accept that (see the unresolved questions).

The machinery is in [implementation.md](./implementation.md).

## Supported loading paths

Registration availability is guaranteed along the build-time-resolved internal static and dynamic imports from configured or plugin-emitted entries. A non-entry output chunk can depend on factories supplied by its known parents. Loading that chunk by its output filename through an unresolved or ignored `import()`, an external module, or an external specifier redirected with `output.paths` is outside this contract. These loading paths can bypass the registrations the chunk needs.

External dependencies are loaded normally, but their own imports are not part of the internal loading graph. Static cycles that pass through external modules and return to generated output, including configured or plugin-emitted entries, are outside this contract: they can reach a reader before its dependencies register the shared code. Modules forming such cycles can be bundled together so their imports are visible to the build, or their shared dependencies can be excluded from inlining.

An unresolved or ignored `import(expression)` stays native. Its runtime value must identify a module available at runtime; this feature does not discover or emit modules named only by that value. The containing common chunk stays a file to preserve relative resolution. This selection restriction is separate from registration placement, which follows the resolved internal edges.

Module loading through code generated by `eval` or `Function` is outside this feature's contract. The loading-path analysis does not infer imports hidden in generated strings or preserve their file-relative resolution. The direct-`eval` selection rules below protect local binding names; they do not extend the contract to generated imports.

For a finite set of runtime choices, a loader map exposes the possible targets to the build:

```js
const plugins = {
  alpha: () => import('./plugins/alpha.js'),
  beta: () => import('./plugins/beta.js'),
};

export function loadPlugin(name) {
  return plugins[name]();
}
```

A module that must be independently loaded by URL can be emitted as an entry. In a plugin's `buildStart` hook, preserve its exports explicitly even though the build uses `preserveEntrySignatures: false`:

```js
this.emitFile({
  type: 'chunk',
  id: './src/plugins/alpha.js',
  fileName: 'plugins/alpha.js',
  preserveSignature: 'strict',
});
```

The entry starts with no assumed prior registrations. Configured `input` entries have the same independent starting path, but `preserveEntrySignatures: false` permits their unused exports to be removed. An alternative is to exclude all shared dependencies of the runtime-loaded module, including transitive dependencies, from inlining. Excluding only the lazy chunk does not preserve those dependencies: a dynamic target already stays a file. Setting `maxSize: 0` disables inlining for the build.

## Design principles / Goals

1. **The unit is a whole common chunk** ([backlog #7](https://github.com/rolldown/backlog/issues/7)). A selected chunk (a "record") keeps its module set, its wrappers and its `exports_to_other_chunks`; nothing is inlined symbol by symbol. This keeps every question ("who owns this symbol", "what does this chunk export") answerable by the existing passes.
2. **A record stays a live chunk.** `ChunkGraph::module_to_chunk`, `chunk.modules`, exec order, namespace decisions and cross-chunk linking never see a difference. The only new state is `InlineCommonChunksState` (selected records, who reads them, who carries them, the names each file chose), owned by the generate stage and read by naming, deconflicting, the finalizer and the renderers. Records use no `PostChunkOptimizationOperation` variant: `Removed` means "merged elsewhere" to its readers, and a record is neither merged nor rendered.
3. **Decide on the final edges, inside the link step.** Selection runs after order lowering, the unused-runtime sweep and the sealing of liveness, on the cross-chunk link derivation itself: derive the final logical edges, select and place, register the registry's runtime demand, derive once more (the demand only adds edges to the runtime chunk; the placement is asserted unchanged), commit. Only afterwards are the logical edges projected onto files (carriers take over a record's imports, imports of records disappear). Nothing after the selection moves a module between chunks.
4. **A carrier owns every copy it prints.** A record's modules are finalized and printed once per carrier, on a clone of their AST, with the carrier's names, and the carrier's deconflict pass names the record's modules together with its own. A file's names come from one renamer and its imports from one table; no name and no text is shared between files, so nothing has to be reserved across them.
5. **A reader carries the factories its loading paths have not registered.** Static dependencies outside the reader's import cycle finish their registrations before its body executes. A dynamic import also starts after the importing file's registrations, so the target and its static dependencies can reuse them. A factory is omitted only when every known path from every configured or plugin-emitted entry supplies it. Registrations inside a static import cycle are not inherited across members, because evaluation order depends on the entry. Factories are printed only in files that read them. See the entry-loading-path analysis below.
6. **Registration comes first along supported loading paths, and the first registration wins.** Every `__share_require(id)` on these paths follows a `__share(id, ...)` that has already run. Registrations and bridges are printed right after a file's imports, before any of the file's own code; a record's own bridges are printed at the top of its factory, which only runs when required. The runtime chunk is imported first.
7. **The runtime stays standalone while the feature is on.** The registry demand appears after every runtime-merge proof has run, so `try_merge_runtime_chunk` returns immediately when the option is enabled. A build with nothing selected therefore differs from the off build by one standalone `rolldown-runtime.js`.
8. **When unsure, keep the file.** Every rule in the selection list below rejects rather than special-cases. A rejected candidate stays a file; one that reads records carries them like any other file.
9. **Runtime demand uses the order wrappers' synthetic-statement channel.** It is registered through the channel `OrderWrapState` already uses for order wrappers, so the sweep gate, the symbol-to-chunk table, deconfliction, the finalizer's runtime filter and the runtime symbol closure all see it.
10. **A record's id is its chunk name plus eight hash characters of its module set** (`shared-ZmCA4nrZ`; [backlog #12](https://github.com/rolldown/backlog/issues/12) asks for short, unique ids). The hash covers the members' stable ids, sorted, and nothing else: the id identifies the record within its build, is the same in every build whose chunk has the same module set, and says nothing about the record's code, so a carrier's bytes move only with its own content. Like webpack's module ids, it does not tell two builds apart. Files of two builds can meet in one page and import the same runtime file, and with it share the registry; the first registration of an id then serves both builds, whatever code each of them holds under it. That is not supported: a page loads the output of one build. Two records of one build under the same name rehash on a collision, as `deconflict_filenames` does. The name keeps the output readable.

## Keeping shared code available for inlining

The two earlier placement optimizations consult the size threshold and the same module-level exclusions as final selection. A common module group that passes these checks stays separate: dynamic already-loaded analysis does not reduce it to one entry, and common-chunk merging does not move it into an entry. This prevents an entry body from trapping the shared code behind an extra trigger facade. Runtime modules are ignored in this preference because runtime placement is separate. Final selection still decides from the completed chunk graph, including cycles, foreign re-exports, wrappers and carrier restrictions; the preference is not a promise that the group will become a record.

A resolved internal dynamic import can be copied: the finalizer computes its target path from each receiving file. That file also takes over the copied record's dynamic-import edges so output metadata and content hashes include the targets. Computed imports and imports ignored by the scanner stay in their original file because the implementation preserves their native resolution base.

Rolldown preserves native `import.meta` in ESM output. A retained `import.meta.url` therefore refers to the output file, and copying it would make the first loaded carrier choose the value. webpack's default replacement uses the source module URL, which has different behavior. The restriction applies only to included statements; a removed function containing `import.meta` does not keep its chunk alive.

## Registration on entry loading paths

Placement first computes the factories each file needs and removes those its static dependencies outside its import cycle register. It then propagates the registrations guaranteed before each file starts evaluating, using the physical file graph after records have been expanded into their importees:

- Each configured and plugin-emitted entry starts with an empty set. An entry that is also dynamically imported still has that independent starting path.
- A static dependency receives only the registrations guaranteed before its importer starts. The importer's own factories have not been registered yet.
- A dynamic target receives those registrations plus the factories the importing file and its static dependencies outside its cycle supply.
- A file reached by several paths receives their intersection. A work queue propagates each reduction until the sets stop changing; nested dynamic loads and cycles use the same rules.

Dynamic imports inside records contribute an edge from every file that can print that record after static placement. Removing redundant copies can only remove edges from this graph, so this analysis can retain an extra factory but includes every dynamic parent in the resolved internal graph. The remaining copies ensure the registrations each dynamic transfer assumes: execution begins at an entry, and a copy is removed only when a prior loading step supplies it. Files outside all entry loading paths retain their static placement.

## Rejected alternatives

- **Per-symbol inlining or code motion.** Would need new ownership rules for symbols and a second finalizer path. The whole-chunk unit reuses everything.
- **Forwarding record exports with ESM `export { x }` in carriers.** Not expressible for a property read; hence the re-export rule above instead of a new emission mode.
- **Projecting edges inside `compute_cross_chunk_link_state`.** That derivation is pure and has two read-only callers that need logical edges (`predicted_static_import_edges`, `lowered_static_import_edges`). Projecting once, after `commit_cross_chunk_links`, keeps a single writer of the physical edges.
- **A `PostChunkOptimizationOperation` variant for records.** Its readers implement "this chunk was merged into another" and "do not render"; a record is live and not rendered, which would have turned two-state checks into three-state ones across the stage.
- **A `globalThis` registry.** A `globalThis` registry would be shared by every build on the page; a runtime-module binding is shared only by files that import the same runtime chunk URL (see Unresolved questions), and it participates in tree shaking, naming and hashing like every other helper.
- **One rendered text per record, shared by its carriers.** Cheaper, but it needs a cross-file naming protocol: records deconflicted first, carriers reserving the records' import bindings and global reads, symbols both import pre-assigned the same name, import declarations merged at render time. Every later change that adds a module-scope binding to rendering would have to know about it, and a miss is a wrong file rather than an error. Per-carrier finalization costs a clone, a finalizer pass and a print per copy of a small record, and keeps every file inside the single-file pipeline.
- **A minimal placement** (pushing a factory down into a chunk several readers share). Choosing a new carrier requires proving every loading path visits it. The placement pass removes redundant copies from existing readers, using static dependencies and entry loading paths.

## Unresolved questions

- A record id does not tell two builds apart (principle 10). Files of two builds that meet in one page and import the same runtime file share one registry, and the first registration of an id wins; the option is for pages that load the output of one build, as webpack's module registry is. A build-specific namespace in the id would keep two builds apart, but every stable choice of it (the input entries, the output directory) is shared by two builds of the same project, and an unstable one would rename every carrier on every build; the question stays open.
- Cost model: `maxSize` bounds the duplicated source, not the duplicated output; a record printed into many files multiplies its bytes. A count limit or a shared-carrier heuristic is future work.
- Dev mode/HMR, `preserveModules`, `onDemandWrapping` and non-ESM formats are out of scope and rejected at option validation.
- The option turns `strictExecutionOrder` on when the user omits it ([backlog #14](https://github.com/rolldown/backlog/issues/14)). Strict execution order is a separate feature with its own open defects: a module with top-level await reachable from a static import cycle can leave the graph unsettled ([rolldown/rolldown#9548](https://github.com/rolldown/rolldown/issues/9548)), which no differential of this feature can see because both sides run under strict order. The option keeps turning it on, so that enabling the feature stays one setting; a project that has not run under `strictExecutionOrder: true` before should enable that first and check its application, then add the option.
- Addons (`banner`, `intro`, `outro` and `footer`), including plugin hooks, apply to emitted files. An inlined chunk shares the addon bindings of the file that registers its factory first. Exclude modules that depend on separate file-local bindings or addon initialization order.
- Vite's SSR manifest and CSS code splitting answer "which chunk owns this module" from a chunk's module list and get several answers for a record's modules; Vite's manifest and modulepreload follow `facadeModuleId`, `imports` and `importedCss`, and a record has no file, so they see only carriers. Vite's CSS plugin emits a style module's CSS from every chunk whose `moduleIds` list it, so a record that holds a style module (a Vue SFC `?vue&type=style` block, an imported `.css` file) gets its CSS copied into every carrier's stylesheet at its execution-order position among the carrier's modules, and its own stylesheet disappears. Until Vite adapts, a Vite build should pass `exclude: /\.(css|scss|sass|less|styl|stylus|pcss|postcss|sss)(\?|$)/` (Vite's own style-file pattern) so such chunks stay files. None of the integrations has been adapted, and Vite must not enable the option on its own until they are.
- A `renderChunk` hook that rewrites code relative to the file's own path makes a record's copies differ between carriers in different directories, and the first registration decides which value every reader sees. The builtin asset and copy module types are kept as files for that reason. Vite's asset URLs under a relative `base` are not such a case: Vite writes them as `new URL(<path relative to the chunk>, import.meta.url)` at render time, so every copy resolves to the same URL; a plugin whose rewrite yields different values in different directories needs `exclude` for the modules concerned.
- A carrier names its own modules and its records' in one pass, so a function or class in either gets a `$1`-style suffix when the other declares the same name: a record symbol when the carrier's own module claims the name first, a carrier symbol when a record module that executes later does. Every carrier registers the same id and the first to run wins, so within one build the `.name` of a record's function or class depends on which carrier a page loads first, and under `minify` the mangled name does too. `output.keepNames` pins the name; without it, code that reads `.name` for anything but logging is a reason to exclude the module.
